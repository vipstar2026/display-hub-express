# إعادة بناء نظام الدفع بالكامل من الصفر

## الهدف
استبدال طبقة الدفع الحالية بالكامل بطبقة موحّدة وآمنة، مع **الحفاظ على الطلبات والمعاملات والفواتير وطرق الدفع الحالية في قاعدة البيانات**. لن تُحذف أي بيانات تاريخية، ولن تُنفّذ أي دفعة حقيقية أثناء البناء أو الاختبار.

## ما سيتم بناؤه

### 1. نواة دفع موحّدة
- تعريف حالات ثابتة لكل محاولة: `created → awaiting_customer → processing → succeeded / failed / cancelled / expired / requires_review / refunded`.
- إنشاء محاولة دفع مستقلة لكل Checkout وربطها بطلب واحد ومعرّف فريد لا يقبل إعادة الاستخدام.
- بوابة نجاح مركزية واحدة فقط تستطيع تحويل الطلب إلى «مدفوع» بعد التحقق من المبلغ والعملة ومرجع الطلب وملكية المحاولة.
- فصل إنشاء الطلب عن إنشاء محاولة الدفع وعن تنفيذ التسليم؛ كل خطوة Idempotent وقابلة لإعادة المحاولة بأمان.

### 2. إعادة كتابة بوابات الدفع الإلكتروني
- **AFS COPYandPAY:** عميل خادم جديد، Checkout جديد، Widget معزول، عودة 3D Secure، Webhook مشفّر، استعلام حالة ومصالحة واسترداد.
- **Benefit/BPay:** Adapter مستقل يستخدم نفس دورة الحالات والتحقق المركزي.
- تصميم Adapter يسمح بإضافة بوابات أخرى لاحقًا دون نسخ منطق الطلب أو النجاح.
- عدم الثقة بنتيجة المتصفح أو بيانات Webhook قبل إعادة التحقق من مزود الدفع.

### 3. الدفع اليدوي
- تحويل بنكي/نقدي/محفظة/طرق يدوية من خلال تدفق موحّد.
- رفع إثبات الدفع بشكل آمن، وحالة `requires_review`، وقبول/رفض إداري مسجّل.
- عدم تسليم المنتج أو اعتبار الطلب مدفوعًا قبل اعتماد مسؤول مخوّل.

### 4. Checkout موحّد
- دمج Checkout العضو والضيف في محرك تسعير وطلب واحد: الأسعار، المخزون، الشحن، الكوبونات، الرسوم والعملة تُحسب على الخادم فقط.
- إبقاء واجهتي العضو والضيف، لكنهما تستدعيان نفس النواة بدل المنطق المكرر.
- توجيه كل بوابة حسب نوعها دون شروط AFS موزعة داخل السلة.
- إبقاء الفصل الحالي بين المنتجات الرقمية والمادية والاستلام والشحن.

### 5. روابط الدفع
- إعادة بناء روابط الدفع فوق نفس الطلبات والمحاولات والتحقق المركزي.
- دعم الانتهاء والإلغاء والدفع مرة واحدة، ومنع إنشاء طلبات أو محاولات مكررة.
- نجاح رابط الدفع يمر عبر نفس بوابة النجاح والتسليم، لا عبر تحديث مباشر مستقل.

### 6. Webhooks والمصالحة والاسترداد
- Route منفصل وآمن لكل مزود مع تحقق التوقيع/التشفير والتحقق من المزود.
- سجل أحداث Sanitized بلا مفاتيح أو بيانات بطاقة.
- Job مصالحة يعالج المحاولات المعلقة فقط ويمنع تحويل unknown إلى failed أو paid دون دليل.
- استرداد كامل/جزئي مربوط بمعاملة ناجحة ومعرّف الدفع الحقيقي، مع منع التكرار.

### 7. لوحة التحكم
- إعادة تنظيم «طرق الدفع» إلى: الطرق، بيانات الربط، وضع الاختبار/الإنتاج، الحدود والرسوم، صحة الاتصال.
- شاشة معاملات موحّدة تعرض المحاولة، الطلب، المزود، الحالة، المراجع والتاريخ دون بيانات حساسة.
- إجراءات مراجعة الدفع اليدوي والاسترداد وإعادة المصالحة بصلاحيات إدارية وتدقيق كامل.
- عدم كشف credentials الخام للمتصفح بعد حفظها؛ القراءة تكون masked والتحديث من خلال server functions محمية.

## حماية البيانات والترحيل
- إضافة schema جديد تدريجيًا بجانب الجداول الحالية، مع `GRANT` وRLS لكل جدول جديد.
- ترحيل وربط السجلات الحالية دون حذف أو تعديل تاريخها المالي.
- إضافة قيود فريدة للمحاولة ومرجع المزود وIdempotency لمنع الازدواج.
- تشغيل النظام الجديد خلف مسار موحّد، ثم تحويل الواجهات إليه، وبعد التحقق تُزال ملفات التنفيذ القديمة فقط؛ تبقى البيانات التاريخية قابلة للعرض.
- لا تُحذف طرق الدفع الحالية أو credentials أثناء الترحيل؛ يتم نقلها/قراءتها وفق البنية الآمنة الجديدة.

## التحقق قبل التفعيل
- اختبارات وحدات للحالات، المبالغ BHD، التحقق من المراجع، Idempotency ومنع النجاح المكرر.
- اختبارات تكامل وهمية لكل مزود: نجاح، رفض، pending، timeout، webhook مكرر، مبلغ/عملة/مرجع خاطئ، استرداد.
- اختبار المتصفح للعضو والضيف وروابط الدفع والدفع اليدوي، على الهاتف وسطح المكتب.
- إثبات أن النجاح وحده يفعّل المخزون الرقمي والفاتورة والبريد مرة واحدة.
- اختبار AFS ببطاقات الاختبار فقط؛ **لا دفع حقيقي**.
- إبقاء الطرق الإلكترونية في وضع الاختبار/معطلة حتى تقرير نهائي ثم تفعيلها يدويًا.

## ترتيب التنفيذ
1. إنشاء النواة وschema والترحيل الآمن.
2. توحيد إنشاء الطلب وCheckout.
3. بناء AFS ثم Benefit عبر Adapters جديدة.
4. بناء الدفع اليدوي وروابط الدفع.
5. بناء Webhooks والمصالحة والاسترداد.
6. ربط الواجهات ولوحة التحكم.
7. اختبارات شاملة، مقارنة البيانات، ثم إزالة كود الدفع القديم بعد ثبوت عدم وجود أي استدعاء له.

## معيار الإنجاز
لا تُعلن الجاهزية إلا عندما تنجح جميع المسارات الوهمية والاختبارات، وتبقى كل الطلبات السابقة ظاهرة، ولا يوجد أكثر من مسار واحد يمكنه تعليم الطلب كمدفوع أو تشغيل التسليم.
